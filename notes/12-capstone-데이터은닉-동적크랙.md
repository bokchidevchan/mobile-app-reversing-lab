# 캡스톤 최종: 데이터 은닉 강화하고 동적으로 크랙

평탄화 라운드에서 "흐름 난독화는 데이터를 안 숨긴다"는 걸 봤다. 그래서 이번엔 데이터 축을 강화했다.
정적 키를 없애고 키를 런타임에 유도하게 만든 뒤, 정적/동적 두 방법으로 뚫었다.

소스: tools/capstone/ios/verify_hard.c, enc_hard.h. 후킹 스크립트: frida-dynamic-crack.js.

## 강화 내용

- 정적 XOR 키 제거. 대신 키스트림을 LCG로 런타임 유도: `s=0x3d; s=(s*31+17)&0xff`.
  .rodata엔 랜덤해 보이는 암호문만 남고, 떼어낼 키 바이트가 없다.
- memcmp로 비교, ptrace(PT_DENY_ATTACH) 안티디버깅 유지.

## 정적 크랙 (더 어려워짐, 그래도 가능)

Ghidra로 check를 보면 키 유도가 그대로 드러난다.

```c
bVar1 = bVar1 * '\x1f' + 0x11;                       // s = s*31 + 17
dec[i] = (&DAT_100003f8f)[i] ^ bVar1;                // 암호문 XOR 키스트림
```

키가 단일 바이트가 아니라 알고리즘이라, 정적으로 풀려면 이 LCG를 읽어 재현해야 한다.
재현해서 바이너리 암호문(0x3f8f, 25바이트)에 적용하니 복원됐다.

복원: `dynamic_beats_static_2026`

즉 데이터를 유도로 숨겨도, 유도 코드가 바이너리에 있으니 읽어서 재현하면 뚫린다. 비용만 올라감.

## 동적 크랙 (키 유도 이해 불필요)

이번엔 키스트림을 전혀 이해하지 않고, 실행 중에 복호된 결과만 가로챘다.
Frida로:

1. ptrace를 no-op으로 교체 -> PT_DENY_ATTACH 안티디버깅 무력화
2. memcmp 후킹 -> 두번째 인자(복호된 정답 25바이트)를 그대로 읽음

```
[+] 런타임 복호된 정답: dynamic_beats_static_2026
```

키 유도가 아무리 복잡해도, 비교 직전엔 평문이 메모리에 떠야 하니 그 순간을 가로치면 끝.

## 빌드 함정 (또 있었다)

-O2가 memcmp를 인라인해서 처음엔 후킹할 호출이 없었다. `-fno-builtin-memcmp`로 실제 호출을
남겨야 후킹됐다. 최적화가 방어/공격 양쪽에 영향을 준다.

## 캡스톤 전체 결론

라운드를 거치며 방어를 계속 올렸다: 네이티브 -> 문자열암호화 -> 안티디버깅 -> 컨트롤 플로우 평탄화
-> 런타임 키 유도. 매 라운드 크랙에 드는 비용은 올라갔지만, 한 번도 못 뚫린 적은 없었다.

- 정적 은닉을 강화할수록 -> 동적 분석이 답이 된다(실행하면 결국 평문이 뜸).
- 동적을 막으려 안티디버깅을 걸어도 -> Frida로 ptrace 한 줄 무력화로 우회된다.
- 진짜 안전은 클라이언트 난독화가 아니라, 비밀을 클라이언트에 두지 않는 설계다.

앱 검수/분석 입장에서 보면 이게 일이다. 앱이 이렇게 겹겹이 숨긴 걸, 정적+동적을 조합해 찾아내야 한다.

## 더 갈 수 있는 곳

- OLLVM/Tigress 정식 도구로 옵티마이저 내성 있는 난독화 vs 크랙.
- 화이트박스 크립토(떼어낼 키 자체를 없앰)로 데이터 은닉의 상한 보기.
- Android .so에도 같은 강화(키스트림+memcmp) 넣고 에뮬에서 Frida 동적 크랙.

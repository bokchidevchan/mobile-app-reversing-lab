# 캡스톤: 실무적으로 "못 뚫는" 형태로 구현

지금까지는 방어를 올려도 다 뚫렸다. 이번엔 "실무적으로 못 뚫는" 걸 목표로,
verify vs use 구분에 맞춰 각각 답을 구현했다.

소스: tools/capstone/ios/verify_secure.c, secure.h.

## 먼저 구분: 확인(verify) vs 사용(use)

- **확인만 하면 되는 비밀**(비번/PIN/라이선스/정답): 원본을 안 두고 검증만 하면 된다 -> 못 뚫게 가능.
- **실제로 써야 하는 비밀**(API 키/복호화 키/토큰): 앱이 값 자체를 메모리에 가져야 함 ->
  클라이언트에선 근본적으로 못 숨김. 답은 서버.

## 확인형: 강한 정답 + salt + 느린 KDF + 난독화

verify_secure.c는 네 가지를 합쳤다.

- 고엔트로피 정답(24자)
- salt + PBKDF2-HMAC-SHA256 20만회 (느린 KDF)
- 컨트롤 플로우 평탄화 + 불투명 술어 (난독화)
- ptrace(PT_DENY_ATTACH) 안티디버깅

검증은 `PBKDF2(입력, salt, 20만) == 저장된 derived key`. 정답 원본은 코드에도 실행 중에도 안 나온다.

### 세 공격 다 실패

- 정적: 바이너리엔 salt(0x3f6f)와 derived key(0x3f7f)만. 단방향이라 역산 불가.
- 동적: Frida로 memcmp 후킹 -> 보이는 건 입력의 PBKDF2 출력과 저장 derived key.
  둘 다 해시라 정답 평문은 안 뜬다. (안티디버깅은 ptrace no-op으로 우회했지만 얻는 게 없음.)
- brute-force: 측정해보니 PBKDF2 20만회라 추측 1회 약 23ms(초당 ~44회).
  24자 고엔트로피 공간 약 10^47 -> 전수 탐색 약 10^38 년. 사실상 불가.

난독화는 뚫려서 "PBKDF2로 검사하는구나"까지는 읽힌다. 하지만 그게 끝이다. 읽어도 정답이 없다.

## 사용형(API 키 등): 클라이언트에선 못 숨긴다 -> 서버

앱이 키를 실제로 써야 하면(예: 서버 API 호출) 그 값이 반드시 메모리에 존재해야 한다.
난독화/암호화로 감싸도 쓰는 순간 Frida로 가로채진다(앞 라운드들에서 계속 그랬다).
그래서 진짜 답은 코드가 아니라 설계다.

- **키를 클라이언트에 넣지 않는다.** 서버가 키를 갖고, 앱은 서버에 요청만 한다.
- 인증이 필요하면 **토큰 방식**: 앱은 사용자 자격증명으로 서버에서 단기 토큰을 받아 쓰고,
  장기 비밀(API 키)은 서버에만 둔다.
- 무결성/정품 확인은 **서버측 검증 + 챌린지-리스폰스**로, 판정 자체를 서버가 한다.

즉 use-secret은 "얼마나 잘 숨기나"의 문제가 아니라 "왜 클라이언트에 뒀나"의 문제다.

## 결론 (캡스톤 총정리)

- 확인형 비밀: 강한 값 + salt + 느린 KDF면 클라이언트에서도 실무적으로 못 뚫는다.
  난독화는 보조일 뿐, 핵심은 "원본을 안 두는" KDF 검증.
- 사용형 비밀: 클라이언트 은닉으론 못 막는다. 서버로 옮기는 게 유일한 정답.
- 이 랩 전체의 한 줄: 클라이언트에 "있는" 비밀은 결국 나온다. 그러니 있게 하지 마라(검증형은 KDF로 없애고, 사용형은 서버로).

## 못 뚫게 만든 요소 요약

| 공격 | 막은 방법 |
|---|---|
| 정적 추출 | 원본 미저장(KDF), salt로 레인보우 무력화 |
| 동적 덤프 | 복호화 안 함 -> 메모리에 평문 없음 |
| brute-force | 고엔트로피 정답 + 느린 KDF(비용↑) |
| (사용형) 런타임 탈취 | 애초에 클라이언트에 안 둠(서버) |

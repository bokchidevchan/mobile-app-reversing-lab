# 서버측 활성화/검증 로컬 데모

클라이언트 은닉의 상한("KDF로 원본 없애기", "사용형은 서버로")을 확인했으니,
그 "서버로" 부분을 로컬에서 직접 구현했다. 라이선스 재사용(복사) 방지가 목표.

소스: tools/activation-server/server.py (stdlib만, 127.0.0.1 전용).
보안: localhost에만 바인딩, HMAC 비밀키는 런타임 생성(커밋 안 함), 개인정보 없음.

## 왜 서버가 필요한가 (복습)

오프라인 서명은 "이 라이선스가 진짜냐"는 증명하지만 "몇 번/어디서 쓰였냐"는 모른다.
서명된 라이선스는 파일이라 복사해서 여러 기기에 붙여도 서명은 다 통과한다.
재사용을 막으려면 상태가 필요하고, 그 상태는 공격자가 리셋 못 하는 곳(서버)에 있어야 한다.

## 구현

- 서버가 비밀(HMAC 키), 유효 라이선스 목록, 활성화 상태(라이선스->기기 집합)를 쥔다.
- POST /activate {license, device_id}: 라이선스를 기기ID에 묶어 등록.
  seat 한도(데모 2대)를 넘으면 거부. 성공 시 토큰 발급.
- POST /verify {license, device_id, token}: 서버가 토큰을 검증.

## 시연 결과

```
동일 라이선스 LIC-AAAA-BBBB, seat 한도 2
device-1 활성화: 200 ok seats_used=1
device-2 활성화: 200 ok seats_used=2
device-3 활성화: 409 seat limit 2 exceeded      <- 재사용(복사) 차단
device-1 재활성화: 200 ok                         <- 이미 등록된 기기는 허용

정상 토큰 verify: ok=true
위조 토큰 verify: ok=false                        <- HMAC 비밀 없이 못 만듦
가짜 라이선스 활성화: 403 invalid license
```

## 핵심

- 판정과 상태가 서버에 있으니, 클라이언트를 아무리 뜯어도 seat 한도를 못 넘는다.
  클라 크랙으로 할 수 있는 건 기껏해야 "이 앱에서 활성화 검사를 건너뛰게 패치"인데,
  그건 그 기기 하나에서만 통하고 서버 상태(다른 기기 활성화 수)엔 영향 없다.
- 토큰은 서버 HMAC 비밀로 서명되니 클라가 위조 못 한다.

## 클라이언트 vs 서버 역할 정리 (이 랩의 최종 그림)

| 하는 일 | 어디서 | 이유 |
|---|---|---|
| 사용자 비밀 확인(비번) | 클라(KDF) 또는 서버 | 원본을 안 두면 클라도 안전 |
| 라이선스 진위 | 클라(공개키 서명검증) | 검증만이라 공개키로 충분 |
| 라이선스 발급 | 서버(개인키) | 발급 권한을 클라에 두면 위조됨 |
| 재사용/시트/유일성 | 서버(상태) | 클라는 복제·리셋 가능 |
| 게임 결과/최종 판정 | 서버 | 클라 조작 무력화 |

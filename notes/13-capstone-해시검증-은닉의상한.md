# 캡스톤: 해시 검증 - 은닉의 상한

지난 라운드들에서 뭘 해도 결국 뚫렸다. 정적으로 암호문+키를 뽑거나, 동적으로 복호된 평문을
memcmp에서 가로챘다. 그럼 "어떻게 하면 더 잘 숨기나?"의 답은 하나다.

**정답을 복호화하지 않는 것.** 정답을 단방향 해시로만 저장하고 hash(입력)==저장해시로 검사한다.
그러면 정답 평문이 코드에도, 실행 중 메모리에도 절대 안 뜬다.

소스: tools/capstone/ios/verify_hash.c, target_hash.h.

## 구현

```c
static int check(const char *in) {
    unsigned char h[32];
    CC_SHA256(in, strlen(in), h);      // 입력을 해시
    return memcmp(h, TARGET, 32) == 0; // 해시끼리 비교 (정답 평문 없음)
}
```

바이너리엔 SHA-256(정답) 32바이트만 박힌다.

## 정적 분석: 해시만 나온다

strings/Ghidra로 봐도 정답 평문은 없고, 저장된 해시(offset 0x3f87)만 있다.
해시는 단방향이라 여기서 정답 역산은 불가능하다.

## 동적 분석: Frida로도 못 꺼낸다

지난 라운드에 잘 통했던 "memcmp 후킹해서 복호된 정답 읽기"를 그대로 해봤다.

```
arg1(입력 SHA-256) = bbf3fa9e58b455e0...   (내가 넣은 guess123의 해시)
arg2(저장된 해시)  = d9fb92e3bbe65be1...   (정답의 해시)
```

둘 다 해시다. 정답 평문은 비교 순간에도 메모리에 없다. 복호화를 안 하니 가로챌 평문이 없는 것.
런타임 덤프 공격이 여기서 처음으로 실패했다.

(빌드 함정 반복: -O2가 memcmp를 인라인해서 처음엔 후킹 안 됨 -> -fno-builtin-memcmp로 해결.)

## 그럼 어떻게 뚫나: brute-force

정답을 못 꺼내니 남는 건 "추측해서 해시가 맞는지 보기"뿐이다. 사전 공격:

```python
for w in wordlist:
    if sha256(w) == TARGET: found = w
# -> opensesame
```

데모 정답 "opensesame"는 약해서 작은 사전으로 바로 뚫렸다.
하지만 정답이 고엔트로피(길고 무작위)면 이 공격도 사실상 실패한다. **거기가 클라이언트 은닉의 상한이다.**

## 정리: 은닉 강도 사다리

| 기법 | 정적 | 동적(Frida) | 남는 공격 |
|---|---|---|---|
| 평문 하드코딩 | 즉시 노출 | - | 없음(이미 뚫림) |
| XOR/AES 암호화 | 키+암호문 뽑기 | 복호 직후 후킹 | - |
| 런타임 키 유도 | 유도 재현 | 복호 직후 후킹 | - |
| 컨트롤 플로우 난독화 | 데이터 그대로 뽑힘 | 동일 | - |
| **해시 검증** | 해시만(역산 불가) | 해시만(평문 없음) | **brute-force뿐** |

## 결론

"더 잘 숨기기"의 끝은 암호화가 아니라 **애초에 평문을 다루지 않는 설계**다.
해시 검증은 정답을 은닉하는 게 아니라 존재 자체를 없앤다. 그래서 정적·동적 추출이 다 실패하고,
정답이 강하면 brute-force도 실패한다.

이건 클라이언트 crackme의 상한이고, 실무 교훈으로 이어진다. 비밀번호/시리얼은 평문/가역암호로
저장하지 말고 강한 해시(+salt, +느린 KDF)로 저장하라. 정답 검증 자체를 서버에 두면 더 낫다.

## 더 갈 곳

- salt + PBKDF2/argon2로 brute-force 비용까지 올리기.
- 안티-Frida(후킹 탐지)로 동적 분석을 아예 막는 라운드 -> 그것도 어떻게 우회되는지.

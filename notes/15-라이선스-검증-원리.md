# 라이선스 검증 원리

캡스톤에서 PBKDF2로 "비밀번호형" 검증을 했는데, 라이선스는 원리가 다르다.
라이선스 키는 사용자가 외우는 비밀이 아니라 벤더가 발급하는 값이고, 보통 고객마다 다르다.
그래서 "해시 하나 저장해두고 비교"로는 안 된다. 실제 모델을 정리한다.

데모 스크립트: tools/license/license-demo.sh (Ed25519, openssl).

## 3가지 모델

### 1. 하드코딩 / 키젠 검사 (약함)

앱이 "이 키가 어떤 수학적 조건(체크섬/포맷)을 만족하나"만 검사한다.
UnCrackable License_01이 이 방식이었고, 검증식을 리버싱해서 keygen을 만들어 뚫었다(notes/08).
검증 로직이 앱에 있으니 유효키를 무한히 찍어낼 수 있다. 근본적으로 약하다.

### 2. 디지털 서명 (제대로 된 오프라인)

공개키 암호를 쓴다.

- 벤더가 개인키로 라이선스(내용 + 서명)를 발급. 개인키는 서버에만 있다.
- 앱엔 공개키만 넣는다. 앱은 서명을 검증만 한다.
- 리버서가 앱을 다 읽어도 공개키와 검증 로직만 보인다. 개인키가 없어서 유효 라이선스를 못 만든다.
- 내용을 조금이라도 바꾸면 서명이 깨진다.

시연 결과(license-demo.sh):

```
[앱] 정상 검증:   Signature Verified Successfully
[공격] 변조 검증:  Signature Verification Failure   (expires 2027->2099)
[공격] 위조 검증:  Signature Verification Failure   (공격자가 자기 키로 서명)
```

이게 "verify vs use"의 정답 적용이다. 앱은 검증만 필요 -> 공개키. 발급 능력(개인키)은 서버에만.

### 3. 온라인 인증 (가장 강함)

앱이 라이선스를 서버로 보내 서버가 판정하고 결과(또는 단기 토큰)를 돌려준다.
검증 로직과 비밀이 다 서버에 있어 위조도 패치도 어렵다.

## 서명 방식의 약점: 패치

서명 방식은 위조는 못 막지만, 검증이 클라이언트에 있으니 공격자가 검증 자체를 건너뛰게
앱을 패치할 수 있다(예: verify() 결과를 항상 true로). 이건 "유효키 만들기"가 아니라 "검사 제거"다.
그래서 실무에선 같이 쓴다:

- 무결성 검사(리패키징 탐지, L3의 CRC 방식)로 패치를 탐지
- 안티디버깅/안티탬퍼
- 결정적으로 중요한 판정은 온라인 인증으로 서버에서

## 정리

| 모델 | 위조(유효키 생성) | 패치(검사 우회) | 리버서가 보는 것 |
|---|---|---|---|
| 하드코딩/키젠 | 쉬움(keygen) | 쉬움 | 검증식 전체 |
| 디지털 서명 | 불가(개인키 필요) | 가능 | 공개키+검증로직 |
| 온라인 인증 | 불가 | 어려움(서버 응답 필요) | 요청/응답만 |

라이선스도 이 랩의 결론과 같다. 발급 권한(개인키)이나 최종 판정을 클라이언트에 두지 마라.
앱엔 "검증만" 시키고, 만들고 판정하는 힘은 서버에 둔다.

## 동일 라이선스 재사용(복사·공유) 막기

서명은 "이 라이선스가 진짜냐"는 증명하지만 "몇 번/어디서 쓰였냐"는 모른다.
서명된 라이선스는 그냥 파일이라 복사해서 여러 기기에 붙여넣을 수 있다. 서명은 다 통과한다.

핵심: 재사용을 막으려면 "상태"가 필요하고, 그 상태는 공격자가 리셋 못 하는 곳(=서버)에 있어야 한다.
순수 오프라인 서명만으로는 복사를 못 막는다(클라이언트는 복제·초기화가 가능하니까).

실무 방법:

- **온라인 활성화 + 시트(seat) 추적**: 활성화 때 라이선스를 기기ID에 묶고, 서버가 "이 라이선스는
  최대 N대"를 강제. 초과하면 거부. 가장 확실한 방법.
- **기기 바인딩(node-locking)**: 서명 페이로드에 기기 지문(하드웨어ID)을 넣어 발급.
  앱이 현재 기기==라이선스 기기인지 검사. 다른 기기로 복사하면 실패.
  단 기기 지문은 위조 가능하고, 그 검사도 패치될 수 있어 오프라인 단독은 약함.
- **플로팅 라이선스 서버**: 동시 사용 토큰을 제한 발급(check-out/check-in). 동시 사용 수 제어.
- **주기적 재검증(heartbeat) + 폐기 목록(revocation)**: 앱이 주기적으로 서버 확인.
  유출된 키를 폐기하거나 동시 사용을 탐지.

즉 "진위"는 오프라인 서명으로 되지만, "유일성/횟수"는 서버 상태가 있어야 한다.
오프라인만 고집하면 UX(인터넷 없이 사용)는 좋아도 복사를 근본적으로 못 막는다.
그래서 상용은 보통 "서명(진위) + 온라인 활성화(유일성)"를 같이 쓴다.

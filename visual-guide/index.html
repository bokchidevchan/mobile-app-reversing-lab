Mobile App Reverse Engineering

앱을 뜯어보며 배운 것들, 그림으로

APK를 여는 것부터, 비밀을 숨기고 다시 뚫는 것까지. 어려운 말 없이 그림으로 정리했어요.

한 줄 결론 먼저 — 클라이언트(앱) 안에 "있는" 비밀은 결국 다 나온다. 숨기는 기술은 시간을 벌 뿐이고, 정말 지키려면 비밀을 아예 앱에 두지 않아야 한다.
01 / 패키지

앱은 사실 압축파일(ZIP)이다

안드로이드 APK도, 아이폰 IPA도 확장자만 다른 ZIP이에요. 풀면 부품들이 나옵니다.

노란 칸이 "실제 코드"예요. 여기가 분석의 핵심입니다. 안드로이드는 classes.dex, 아이폰은 Mach-O.

02 / 코드 형태

안드로이드는 "반쯤 사람 글", 아이폰은 "기계어"

같은 리버싱인데 난이도가 다른 이유는 코드가 만들어지는 방식이 다르기 때문이에요.

Android · DEX

바이트코드 → jadx로 되돌림

이름·구조가 많이 남아서 Java 소스에 가깝게 복원돼요. 읽기 쉬움.

if (a.a(input)) {
    setTitle("Success!");
}
iOS · Mach-O

기계어 → Ghidra로 "의사 C"

소스로 못 되돌려요. 디스어셈블/디컴파일러를 한 겹 더 거칩니다.

mov  x8, #0xf
ldr  x0, [x9]
bl   _strcmp   ; ← 어셈블리
03 / 분석 두 방식

안 켜고 읽기(정적) vs 켜고 훔쳐보기(동적)

비밀을 아무리 숨겨도, 앱이 실제로 쓰려면 언젠가 메모리에 평문으로 뜬다. 그 순간을 노린다.

04 / 비밀 숨기기

숨기는 강도 사다리 — 그리고 어디서 뚫리나

직접 만든 앱에 방어를 한 층씩 올리고 매번 다시 뚫어봤어요. 결과를 badge로 표시했습니다.

1
평문 하드코딩정답을 코드에 그대로
즉시 노출
2
XOR / AES 암호화키와 암호문이 코드에 함께 있음
키 꺼내 복호화
3
네이티브(.so)로 이동jadx는 막히지만 Ghidra엔 열림
Ghidra로 읽음
4
런타임 키 유도 + 컨트롤 플로우 난독화흐름이 스파게티가 됨
Frida로 런타임 탈취
5
해시 검증 (SHA-256)정답을 저장 안 하고 지문만 비교
정적·동적 실패
약하면 brute-force
6
강한 정답 + salt + 느린 KDF(PBKDF2)추측 1회에 큰 비용
사실상 못 뚫음

핵심: 1~4는 "숨기기"라 결국 찾으면 나온다. 5~6은 정답을 아예 안 두는 설계라 뽑을 게 없다. 단, 이건 "확인만 하면 되는 비밀"(비번/정답)에만 통한다.

05 / 공개키 · 개인키

공개키 / 개인키, 밀랍 봉인으로 이해하기

열쇠가 두 개예요. 하나는 "찍는 도장", 하나는 "진짜인지 알아보는 눈". 도장 없이는 같은 봉인을 못 찍습니다.

🔑 개인키 (Private)

도장. 벤더/서버만 가짐. 절대 배포 안 함.
이걸로만 서명(발급)할 수 있어요.

👁️ 공개키 (Public)

알아보는 눈. 아무한테나 줘도 됨. 앱에 넣어도 안전.
이걸로는 검증만 되고 서명은 못 해요.

직접 해보기 (시뮬레이션)

서명 → 검증 → 변조 실험

서명 버튼을 눌러 시작하세요.

＊브라우저 안 시뮬레이션이에요. 실제로는 openssl로 Ed25519 서명(64바이트)을 만들고 검증합니다. 원리는 동일: 내용이 조금이라도 바뀌면 서명이 깨져요.

봉인이 못 하는 것 (오해 주의)
비밀 유지 ✗

암호화가 아니라 봉인. 내용은 그대로 읽힘.

복사 방지 ✗

서명된 파일은 복사해도 유효 → 서버 필요.

검사 우회 ✗

검증 코드를 통째로 패치하면 무시됨.

06 / 어디서 지키나

확인(verify)은 앱에서, 사용(use)·판정은 서버에서

"이 값을 확인만 하면 되나, 실제로 써야 하나?"가 전부예요.

지켜야 할 것어디서왜
사용자 비밀번호 확인앱(KDF) 또는 서버원본을 안 두면 앱에서도 안전
라이선스 진위앱 (공개키 검증)검증만이라 공개키로 충분
라이선스 발급서버 (개인키)발급 권한을 앱에 두면 위조됨
재사용/시트/유일성서버 (상태)앱은 복제·초기화 가능
결제·게임결과 최종 판정서버클라 조작을 무력화
API 키 등 실제 쓰는 비밀서버앱에 있으면 쓰는 순간 메모리에서 탈취됨

실제로 로컬 활성화 서버를 만들어, 같은 라이선스를 3번째 기기에서 쓰려 하면 409 seat 초과로 막히는 것까지 확인했어요. 클라를 아무리 뜯어도 서버가 쥔 "몇 대 썼나"는 못 바꿉니다.

07 / 네트워크

앱이 밖으로 뭘 보내나 (mitmproxy)

가운데에 프록시를 끼워 TLS를 대신 맺으면, 앱의 CA 신뢰 여부에 따라 통신이 보이거나 막힌다.

CA 신뢰 안 함

위조 인증서라 앱이 거부 → 안 보임.

CA 신뢰함

복호화되어 ?token=ABC123까지 노출.

SSL Pinning

특정 인증서만 믿어 거부 → Frida로 우회.

08 / 전체 지도

지금까지의 스터디 지도

뜯기(공격)와 지키기(방어)는 같은 지식의 양면이에요.

뜯기 (분석)
  • APK/IPA 구조 열기
  • jadx / Ghidra로 코드 읽기
  • Frida로 런타임 후킹 (키·정답 탈취)
  • mitmproxy로 통신 가로채기
  • 권한·트래커·URL 정적 감사
지키기 (방어)
  • 난독화·네이티브·안티디버깅 (시간 벌기)
  • 해시/KDF로 정답 원본 없애기
  • 공개키 서명으로 위조 차단
  • 서버로 발급·유일성·최종판정 이관
  • SSL Pinning으로 통신 보호
다시 한 줄 — 방어는 비용을 올릴 뿐 완벽하지 않다. 그래서 진짜 중요한 비밀은 클라이언트에 두지 않는다. 확인용은 KDF로 없애고, 사용·판정은 서버로.

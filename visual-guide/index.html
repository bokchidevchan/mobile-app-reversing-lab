Mobile App Reverse Engineering

앱을 뜯어보며 배운 것들, 그림으로

APK를 여는 것부터 비밀을 숨기고 다시 뚫는 것까지. 왼쪽 목록에서 하나씩 골라 보세요.

한 줄 결론 먼저 — 클라이언트(앱) 안에 "있는" 비밀은 결국 다 나온다. 숨기는 기술은 시간을 벌 뿐이고, 정말 지키려면 비밀을 아예 앱에 두지 않아야 한다.
뜯기

jadx·Ghidra로 읽고, Frida로 런타임에 가로채고, mitmproxy로 통신을 본다.

지키기

난독화는 시간벌기. 해시/KDF로 원본을 없애고, 서명·서버로 판정을 옮긴다.

한계

클라 방어는 완벽할 수 없다. 진짜 비밀은 서버에.

01 / 패키지

앱은 사실 압축파일(ZIP)이다

안드로이드 APK도, 아이폰 IPA도 확장자만 다른 ZIP. 풀면 부품들이 나옵니다.

노란 칸이 "실제 코드"예요. 여기가 분석의 핵심. 안드로이드는 classes.dex, 아이폰은 Mach-O.

02 / 코드 형태

안드로이드는 "반쯤 사람 글", 아이폰은 "기계어"

같은 리버싱인데 난이도가 다른 이유는 코드가 만들어지는 방식이 다르기 때문이에요.

Android · DEX

바이트코드 → jadx로 되돌림

이름·구조가 많이 남아 Java 소스에 가깝게 복원돼요. 읽기 쉬움.

if (a.a(input)) {
    setTitle("Success!");
}
iOS · Mach-O

기계어 → Ghidra로 "의사 C"

소스로 못 되돌려요. 디스어셈블/디컴파일러를 한 겹 더 거칩니다.

mov  x8, #0xf
ldr  x0, [x9]
bl   _strcmp   ; ← 어셈블리

안 켜고 읽기(정적) vs 켜고 훔쳐보기(동적)

06 / 공개키 · 개인키

07 / 어디서 지키나

확인은 앱에서, 사용·판정은 서버에서

딱 하나만 물어보면 돼요. "이 값을 확인만 하면 되나, 실제로 써야 하나?"

확인(verify)만 하면 됨

"이 입력이 맞아?"만 판단. 원본을 안 가져도 됨.

08 / 네트워크

앱이 밖으로 뭘 보내나 (mitmproxy)

HTTPS는 앱과 서버 사이를 자물쇠로 잠근 통신이에요. 가운데서 읽으려면 조건이 있습니다.

🔒 먼저 비유로

HTTPS = 봉인된 편지를 주고받는 것. 중간 우체부는 못 읽어요.
mitmproxy = 중간에 앉은 우체부. 편지를 열어 읽으려면, 앱이 "이 우체부의 봉인도 진짜로 인정한다"고 믿어줘야 합니다.
앱이 누굴 믿는지는 신뢰 목록(CA 목록)에 달렸어요. 우체부가 그 목록에 없으면 → 앱이 거부 → 못 읽음.

① 그냥 프록시만 껴봤어요. 앱은 낯선 인증서라 거부합니다.
SSL Pinning이 뭔데 CA를 설치해도 막히나?

보통 앱은 "신뢰 목록에 있으면 OK"예요. 그래서 mitm CA를 목록에 넣으면(②) 통과했죠.
Pinning은 한 단계 더 깐깐합니다. 앱이 "진짜 서버 인증서의 사진"을 미리 품고 있어서, 목록에 있든 없든 그 사진과 정확히 같은 것만 받아요. mitm 인증서는 사진과 다르니 거부(③).
우회(④)는 실행 중에 Frida로 그 "사진 대조" 코드를 꺼버리는 거예요. 그러면 다시 목록만 보고 통과합니다.

그래서 pinning이 걸려 있다는 것 자체가 "이 통신은 특히 감추고 싶어한다"는 신호이기도 해요. 검수 때 눈여겨봅니다.

09 / 난독화 도구

난독화 도구는 각자 뭘 하나

"난독화"라고 다 같은 게 아니에요. 도구마다 막는 축이 다릅니다. 리버서가 겪는 난이도도 달라요.

난독화가 하는 5가지 (축)
이름 바꾸기

클래스·메서드를 a,b,c로. 읽기 귀찮게. (로직·문자열은 그대로)

문자열 암호화

"secret"을 지우고 런타임에 복호. strings에 안 뜸.

흐름 난독화

순차 코드를 상태머신으로 흩어 디컴파일러를 방해.

네이티브 이동 / 패킹

코드를 .so로 내리거나 dex를 암호화해 껍데기만 남김.

OLLVM (네이티브)—일부O(강)네이티브 전용

10 / 실전 앱 분석

하드닝된 진짜 앱은 이렇게 생겼다

연습용 crackme와 달리, 상용급 앱(예: OWASP L4 "r2pay")은 방어를 겹겹이 쌓아요. 분석 순서가 중요합니다.

구조부터 다르다 (r2pay 예) 
classes.dex            ← 얇음(UI/글루). jadx로 봐도 로직 거의 없음
lib/*/libnative-lib.so   ← 1.7MB, 진짜 로직/토큰화 (난독화 가능)
lib/*/libtool-checker.so ← 탐지 전용 (= RootBeer 루트탐지 라이브러리)
JNI: gXftm3iswpkVgBNDUp  ← 난독화된 이름으로 네이티브 진입

"jadx 열었더니 앱이 아무것도 안 한다"면 로직이 네이티브에 있다는 신호. 프레임워크·네이티브부터 의심.

분석 순서 (겹겹 방어 뚫기)
①
정체 파악프레임워크·네이티브 라이브러리·JNI 경계 확인 (apk-audit)
②
탐지층 규명libtool-checker = RootBeer. checkForRoot가 su 경로 존재를 셈
③
탐지 우회Frida로 checkForRoot → false. 앱이 안 죽게
④
핵심 로직 분석libnative-lib.so를 Ghidra로. 너무 크면 Frida로 입출력 관찰하며 좁힘
⑤
플래그 추출토큰화/검증 규칙 역추적 → 다단계 플래그

교훈: 실전 앱은 "정적/동적/안티탐지 우회"를 다 섞어야 하는 종합판. 로직과 탐지를 네이티브로 내리고 JNI 이름까지 가린 게 상용 보호에 가장 가깝다.

11 / 심화 관문

실무에서 진짜 막히는 두 관문

도구를 다 갖춰도 여기서 자주 멈춰요. 왜 막히고 어떻게 넘는지만 알아두면 됩니다.

① Android 14에서 mitmproxy가 안 통한다

HTTPS를 보려면 mitm 인증서를 시스템 신뢰 목록에 넣어야 하는데, Android 14는:

  • /system이 read-only (verity) → 그냥 복사 불가
  • 인증서 저장소가 conscrypt APEX로 이동 → 위치도 다름

넘는 법: cacerts 디렉토리에 tmpfs를 덮어씌우고(bind-mount) 기존+mitm 인증서를 채운다. 단 APEX는 마운트 네임스페이스가 분리돼 있어, 앱이 보는 곳에 반영하려면 nsenter로 zygote 네임스페이스에 들어가 마운트해야 한다. (user 인증서는 앱이 기본 불신 — network_security_config)

② Flutter 앱은 프록시·시스템 CA를 무시한다

Flutter는 코드가 libapp.so(Dart AOT 스냅샷)에 있어 jadx가 무의미하고, 네트워크도 특이해요.

  • Dart 네트워킹은 시스템 프록시를 안 탐 → mitm 켜도 안 잡힘
  • Dart가 자체 CA 번들 사용 → 시스템에 mitm CA 넣어도 소용없음

넘는 법: reFlutter로 엔진(libflutter.so)을 패치해 프록시/CA를 강제하거나, Frida로 Dart의 SSL 검증을 후킹. 스냅샷 자체는 blutter로 파싱해 클래스/메서드 복원. "mitm 켰는데 아무것도 안 잡힌다" → Flutter 의심.

③ 더 센 난독화 (참고)

OLLVM은 컴파일러 수준에서 흐름을 흩어 Ghidra 디컴파일을 스파게티로 만든다(손 평탄화와 달리 옵티마이저 내성). 화이트박스 크립토는 "떼어낼 키" 자체를 없앤다. 이 지점부터는 정적이 매우 힘들어 동적·계측 위주로 간다.

09 / 전체 지도

지금까지의 스터디 지도

뜯기(공격)와 지키기(방어)는 같은 지식의 양면이에요.

뜯기 (분석)
  • APK/IPA 구조 열기
  • jadx / Ghidra로 코드 읽기
  • Frida로 런타임 후킹(키·정답 탈취)
  • mitmproxy로 통신 가로채기
  • 권한·트래커·URL 정적 감사
지키기 (방어)
  • 난독화·네이티브·안티디버깅(시간벌기)
  • 해시/KDF로 정답 원본 없애기
  • 공개키 서명으로 위조 차단
  • 서버로 발급·유일성·최종판정 이관
  • SSL Pinning으로 통신 보호
다시 한 줄 — 방어는 비용을 올릴 뿐 완벽하지 않다. 그래서 진짜 중요한 비밀은 클라이언트에 두지 않는다. 확인용은 KDF로 없애고, 사용·판정은 서버로.

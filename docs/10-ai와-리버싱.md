# 10. AI와 리버싱 — 쉬워지는 것 vs 사람이 해야 하는 것

"요즘 AI 돌리면 리버싱 쉬운 거 아냐?"에 대한 정리. 많이 쉬워진 건 맞지만 축이 갈린다.

## AI가 확 쉽게 해주는 것 (읽기·설명·스크립팅)

- 디컴파일 결과 해석: Ghidra 의사 C나 jadx Java를 붙여넣고 "이거 뭐하는 코드야" → 잘 해줌
- 뭉개진 이름(a, b, local_70) 의미 추론, 변수명 제안
- Frida/reFlutter/후킹 스크립트 작성
- 개념·알고리즘 설명, 어느 함수부터 볼지 방향 잡기
- 큰 코드에서 문자열·호출 흐름 찾기

= 숙련된 파트너가 옆에 붙은 셈. 여기선 AI가 확실히 속도를 올린다.

## 여전히 사람이 해야 하는 것 (실행·검증)

- 실제로 실행하고 환경을 세팅하는 일 (에뮬레이터/기기, frida-server, 프록시)
- 버전 맞춘 도구 빌드 (blutter, hermes-dec 등 — 대상 버전과 안 맞으면 무용)
- 동적 계측, 안티디버깅/안티탐지 우회를 실제로 돌리기
- 패킹·화이트박스 같은 물리적 장벽 넘기
- **AI의 "자신 있는 오답" 검증** — 리버싱은 저수준·버전종속이 많아 AI가 그럴듯하게 틀린다

AI는 님 환경에서 뭘 실행해주지 않는다. 리버싱의 본질(가설 → 실제 바이너리/런타임으로 검증)의
검증 쪽은 그대로 사람 몫이다.

## 이번 스터디에서 AI가 "자신 있게 틀린" 것들

전부 직접 돌려보고서야 잡혔다. "그냥 AI한테 물어봐"였으면 확신에 찬 오답으로 넘어갔을 것들:

- Frida 17에서 Java 브리지 분리 → `Java is not defined`. 16.7.19로 맞춰 해결.
- `-O2`가 XOR을 상수폴딩 → 평문이 바이너리에 박힘. `volatile`로 수정.
- `-O2`가 memcmp 인라인 → 후킹 대상 소멸. `-fno-builtin-memcmp`로 해결.
- otool 리틀엔디언 워드 파싱 → `fgal` vs `flag`. 파일에서 자연 순서로 직접 읽어 교정.
- "이 앱은 루트 탐지에 죽는다" 단정 → 실제론 su가 앱 PATH에 없어 안 걸림.
- Android 14 system CA 설치 → read-only(verity)+APEX 벽. 돌려보고서야 확인.

## Flutter(libapp.so)가 특히 "그냥 AI"가 안 되는 케이스

- Dart AOT 스냅샷은 버전마다 바뀌는 커스텀 포맷 → 바이트를 AI에 던지면 지어낸다.
- 실제 작업은 "엔진 버전 확인 → 맞는 blutter 빌드 → 실행해 이름 복원"인데 이건 추론이 아니라 실행·노가다.
- --obfuscate면 이름조차 안 남아 동적으로 가야 한다.
- 즉 대부분 타깃보다 "그냥 AI로 끝"이 덜 통하는 축이다.

## 결론

실력의 핵심이 옮겨갔다: "정답을 아느냐"에서 **"AI가 틀렸는지 알아채고 도구로 검증할 수 있느냐"** 로.
AI는 강력한 코파일럿이지만, 실행과 검증은 사람이 한다. 리버싱·보안 검수가 특히 그렇다.

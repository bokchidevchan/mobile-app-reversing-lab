# 07. 공개키 서명 검증

라이선스 검증(notes/15)과 활성화(notes/16)에서 쓴 핵심 개념. 원리를 따로 정리한다.
데모 스크립트: tools/signature-demo.sh (Ed25519, openssl).

## 비대칭 암호: 열쇠가 두 개

대칭키는 잠그는 열쇠 = 여는 열쇠(하나). 공개키 암호는 수학적으로 짝인 열쇠 두 개를 만든다.

- 개인키(private): 소유자만. 절대 배포 안 함.
- 공개키(public): 아무한테나 줘도 됨. 앱에 넣어도 됨.

핵심: 공개키로 개인키를 역산할 수 없다. 그래서 공개키는 공개해도 안전하다.

## 두 가지 용도

- 암호화(비밀 유지): 공개키로 잠그고 개인키로 연다.
- 서명(진위 증명): 개인키로 서명하고 공개키로 검증한다. <- 라이선스가 쓰는 것.

## 서명 만들기 / 검증하기

서명(개인키 소유자):

1. 메시지를 해시 -> 고정 길이 지문(그래서 메시지 길이와 무관하게 서명 크기 일정)
2. 그 지문에 개인키로만 가능한 연산 -> 서명
3. 메시지 + 서명 배포 (메시지 자체는 안 숨겨짐)

검증(공개키만 가진 앱):

1. 받은 메시지를 직접 해시 -> 지문 A
2. 공개키 + 서명으로 "이 서명이 지문 A에 대응하나" 검사
3. 맞으면 통과

동시에 둘을 보장한다.

- 무결성: 메시지를 조금이라도 바꾸면 지문이 달라져 서명 불일치 -> 실패
- 진위: 그 개인키로 서명한 게 아니면 통과 못 함

## 왜 안전한가

개인키만이 공개키가 인정하는 서명을 만든다. 공개키는 검증만 되지 서명은 못 한다.
그래서 앱에 공개키를 박아도, 리버서가 공개키와 검증 코드를 다 봐도 개인키가 없어 위조 불가.
이게 "verify vs use"의 적용: 앱은 검증만 필요 -> 공개키. 발급(서명 생성)=개인키는 서버에만.

## 데모로 확인 (tools/signature-demo.sh)

```
서명 크기: 64 바이트 (Ed25519 고정)

1) 원본 검증:              Signature Verified Successfully
2) 메시지 한 글자 변경:    Signature Verification Failure   (2027 -> 2028)
3) 서명 1비트 훼손:        Signature Verification Failure
4) 공개키로 서명 시도:     Could not find private key from pub.key
```

## RSA vs Ed25519

- RSA: 서명 = 지문을 개인키 지수로 거듭제곱(mod n), 검증 = 공개키로 되돌려 비교. "개인키로 잠그고 공개키로 푸는" 그림.
- Ed25519: 타원곡선 기반. 틀은 다르지만 개인키=서명 / 공개키=검증 역할은 같음. 빠르고 서명 64바이트로 작고 안전한 기본값.

## 보장하는 것 / 못 하는 것 (오해 주의)

보장: 위조 불가(진위), 변조 감지(무결성), 부인 방지.

못 하는 것:
- 비밀 유지 아님. 서명은 암호화가 아니라 봉인. 메시지 내용은 그대로 읽힌다.
- 복사/재사용 방지 아님. 서명된 파일은 복사해도 유효 -> 서버 상태(seat) 필요(notes/16).
- 검사 우회 방지 아님. 검증이 클라에 있으면 verify()를 true로 패치 가능 -> 무결성검사/온라인으로 보완.

## 한 줄 비유

밀랍 봉인. 도장(개인키)은 벤더만, 봉인이 진짜인지 알아보는 눈(공개키)은 누구나.
진위는 아무나 확인하지만 도장 없이는 같은 봉인을 못 찍는다.
봉인은 내용물을 가리지도(암호화 아님), 복사를 막지도(상태 필요), 무시(패치)를 막지도 못한다.

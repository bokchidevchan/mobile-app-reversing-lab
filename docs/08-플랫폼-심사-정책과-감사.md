# 08. 플랫폼 심사 정책과 정적 감사

검수 관점에서, 앱이 Google Play / App Store 정책과 국가별 규제를 지키는지 리버싱으로 미리 본다.
정책을 다 외우기보다, "정책이 바이너리에서 어떻게 드러나나 + 어떻게 자동으로 1차 스캔하나"를 정리한다.

도구: tools/apk-audit.py (aapt2 기반, 실행 없이 정적 스캔).

## 주요 정책 축 (Play / App Store 공통 성격)

- **데이터 안전/개인정보**: 어떤 데이터를 수집·전송하는지 신고(Play Data safety / App Store Privacy Nutrition Label)와
  실제 동작이 일치해야 함. 몰래 수집/전송하면 위반.
- **권한 최소화**: 기능에 불필요한 위험 권한(위치/연락처/마이크/SMS 등) 요구 금지. 민감권한은 정당성 필요.
- **제한 API**: QUERY_ALL_PACKAGES, 접근성 오남용, SMS/통화기록 등은 별도 승인/제한.
- **기만 행위**: 숨은 기능, 리패키징, 원격으로 코드 받아 실행(동적 코드 로딩) 등.
- **광고/추적**: 광고 ID 사용 규칙, 아동 대상 앱의 추적 제한.
- **금융/도박/콘텐츠**: 국가별로 허용 범위가 다름 -> 지역별 규제.

## 정적 감사가 잡는 신호 (apk-audit.py)

일부러 취약하게 만든 데모 APK에 돌린 결과:

```
## 위험 플래그
  - debuggable=true (릴리스에 있으면 안 됨)
## 권한
  - ACCESS_FINE_LOCATION [위험]
  - READ_CONTACTS [위험]
  - RECORD_AUDIO [위험]
  - QUERY_ALL_PACKAGES [위험]
## 트래커/광고 SDK 신호
  - Google AdMob (com.google.android.gms.ads)
  - AppsFlyer (com.appsflyer)
## 하드코딩된 엔드포인트
  - http://tracking.example.com/collect?uid=123
```

각 신호가 정책과 이렇게 연결된다.

- debuggable=true: 릴리스 빌드 규정 위반 + 보안 취약(디버거 접속 허용)
- 위험 권한: 데이터 안전 신고와 대조. 기능상 불필요하면 과다 수집 의심
- QUERY_ALL_PACKAGES: 제한 권한. 정당성 없으면 심사 반려 사유
- 트래커 SDK: 개인정보 수집/광고 추적 -> Data safety 신고 누락 시 위반
- 하드코딩 http 엔드포인트: 평문 전송(개인정보면 규제 위반), 몰래 하는 전송 후보

## 도구의 한계 (1차 스캐너)

- "위반"을 단정하지 않는다. 검토 후보를 모아 사람이 판단하게 돕는다.
- 매니페스트 플래그(allowBackup/cleartext) 파싱은 aapt2 xmltree 근사라 정밀 확인은 apktool 디코드로.
- 트래커/URL은 dex 문자열 기반이라 난독화/문자열암호화된 앱에선 놓칠 수 있음 -> 동적 분석(네트워크 캡처)으로 보완.

## 정적 + 동적 조합

정적 감사로 "무엇이 있나"(권한/SDK/URL)를 빠르게 훑고,
네트워크 캡처(notes/17)로 "실제로 무슨 데이터가 어디로 나가나"를 확인한다.
둘을 합쳐야 "신고와 실제 동작이 일치하나"를 검증할 수 있다.

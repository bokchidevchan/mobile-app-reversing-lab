# 06. 난독화와 보호 기법

앱이 값을 숨기고 분석을 방해하는 방법들. 개발자(방어) 입장에서 뭘 하는지 알아야
리버서(분석) 입장에서 뭘 마주칠지 안다. L1/L2에서 본 것들이 여기 다 들어간다.

## 값을 숨기는 기법 (구현 관점, 난이도 순)

**1) 문자열 분할 / 스택 스트링**
문자열을 통째로 `.rodata`에 두지 않고 런타임에 조립한다.

```c
// 나쁨: strings에 그대로 노출
const char *k = "SECRET_KEY";
// 나음: 조각으로, 런타임 조립
char k[11]; k[0]='S'; k[1]='E'; /* ... */
```

L2의 `"he fish"`가 숫자 `0x68736966206568`로 박힌 게 이 결과다. 컴파일러가 스택 지역 문자열을
명령어 즉시값(immediate)으로 채워서, strings(.rodata만 훑음)에 안 잡혔다.

**2) 컴파일타임 XOR**
저장은 XOR된 상태, 쓸 때만 푼다. iOS 데모가 이것.

```c
static const unsigned char ENC[] = { /* secret ^ 0x2b */ };
for (int i=0;i<n;i++) buf[i] = ENC[i] ^ 0x2b;
```

C++이면 constexpr로 컴파일 시점에 XOR해서 소스에도 평문이 안 남게 할 수 있다.

**3) 런타임 암호화 (AES)**
암호문+키를 넣고 실행 중 복호화. L1 방식. 단 키가 같이 있어야 해서 정적으로 털린다.

**4) 네이티브로 이동 (JNI)**
검증/핵심 로직을 .so로 내린다. L2 방식. jadx로는 안 보이게 되지만 Ghidra엔 열린다.

```java
public native boolean bar(byte[] in);
```

**5) 안티디버깅**
디버거/Frida가 붙으면 동작을 막는다. L2가 ptrace를 썼다.

```c
if (ptrace(PTRACE_TRACEME, 0, 0, 0) == -1) exit(1);
// 또는 /proc/self/status의 TracerPid, getppid 검사
```

**6) 심볼 스트립**
내부 함수 이름을 지워 nm에 안 나오게. JNI 함수는 이름이 필요해서 남긴다.

**7) 컨트롤 플로우 난독화**
OLLVM 등으로 흐름을 뒤섞어(flattening, opaque predicate) 디컴파일 결과를 스파게티로 만든다.
로직은 같은데 읽기가 어렵다.

**8) 패킹 / 화이트박스 크립토 (강함, 도구 필요)**
- 패킹: dex/so를 암호화해두고 실행 시 메모리에서 풀어 로드. 정적으론 껍데기만.
- 화이트박스 크립토: 키를 알고리즘 테이블에 녹여 "떼어낼 키" 자체를 없앤다.

## Android 난독화 도구 비교

### ProGuard / R8 (기본)

R8이 요즘 Android 기본(ProGuard 대체). 둘 다 하는 일은 사실상 셋이다.

- 축소(shrinking): 안 쓰는 코드 제거
- 최적화(optimization): 인라이닝 등
- 이름 난독화(renaming): 클래스/메서드/필드를 a, b, c로

안 하는 게 중요하다. **문자열 암호화 안 함(평문 노출), 컨트롤 플로우 난독화 안 함, 안티디버깅 안 함.**
그래서 ProGuard/R8만 걸린 앱은 jadx로 멀쩡히 디컴파일되고 이름만 의미 없다. L1에서 본
`sg.vantagepoint.a.a`, `a()`, `b()`가 이 renaming의 모습. mapping.txt로 원래 이름 복원도 된다(개발자용).

### Allatori (상용)

ProGuard가 하는 걸 다 하고 더 한다. 핵심 추가 둘.

- **문자열 암호화**: `"secret"`을 지우고 암호화 형태 + 복호화 호출로 바꾼다.

```java
// 원본
String key = "SECRET_KEY";
// Allatori 후 (jadx로 보면)
String key = a.a("ਢ...");   // 암호문 + 주입된 복호화 메서드
```

정적으론 평문이 안 보이고, 값을 얻으려면 실행하거나(Frida) 복호화 메서드를 재현해야 한다.

- **컨트롤 플로우 난독화**: 흐름을 뒤섞어 jadx가 이상한 goto를 뱉거나 실패. smali로 내려가 읽어야 할 때가 있다.
- 그 외: 디버그 정보 제거, 공격적 renaming(오버로딩으로 이름 재사용), 워터마킹, 일부 무결성 체크.

단 Allatori는 바이트코드(DEX) 레벨이다. 네이티브 이동이나 dex 패킹은 안 한다.

### DexGuard (상용, 더 강함)

Allatori류 + 네이티브 코드 암호화, 리소스/자산 암호화, dex 패킹, 강한 무결성/루팅 탐지까지.
상용 보호의 상위. 실제 금융/게임 앱에서 본다.

## 비교표

| | ProGuard / R8 | Allatori | DexGuard | (참고) L2 |
|---|---|---|---|---|
| 이름 난독화 | O | O | O | 일부 |
| 문자열 암호화 | X | O | O | 조각 분할 |
| 컨트롤 플로우 난독화 | X | O | O | X |
| 안티디버깅/루팅탐지 | X | 일부 | O | O (ptrace) |
| 네이티브 이동/패킹 | X | X | O | O |
| 동작 레벨 | DEX | DEX | DEX + 네이티브 | 네이티브 |

## 리버서 입장에서 체감

- ProGuard/R8만: jadx로 다 보임. 이름이 a/b/c라 읽기 귀찮을 뿐. 난이도 낮음.
- Allatori: 문자열 암호화 + 흐름 꼬임으로 한 단계 올라감. 그래도 DEX라 jadx+동적으로 뚫림.
- DexGuard/네이티브/패킹: Ghidra + 동적(안티디버깅 우회)까지 총동원. 축이 다름.

## 한계 (핵심)

이 전부가 불가능하게 만드는 게 아니라 비용을 올리는 것이다. 앱이 값을 쓰려면 결국 메모리에
평문/키가 떠야 하고, 그 순간을 Frida로 잡으면 정적 방어가 아무리 세도 뚫린다.
실제로 이번에 CCCrypt/AES를 후킹해서 키를 그냥 가져왔다.

그래서 결론 둘.

- 방어 측: 여러 축을 겹쳐(renaming + 문자열암호화 + 네이티브 + 안티디버깅 + 무결성) 비용을 올린다. 시간 벌기.
- 근본: 진짜 비밀(정답 검증, API 키)은 클라이언트에 두지 말고 서버에 둔다.
